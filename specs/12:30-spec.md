# Dispatch Agent: Build Spec

Oct 17, 2026 x

## 1. Overview

Dispatch Agent is an autonomous logistics agent that plans multi-stop delivery routes with shortest-path algorithms, detects disruptions, re-plans, and notifies customers with no human in the loop. Built for the GDG Agentic Hackathon (Agent Wars), problem statement: Logistics Handler.

**Pitch:** most teams will build "enter A and B, get a route". Ours runs a sense, decide, act loop: a disruption hits, the agent triages it, re-optimizes routes, explains why, and messages affected customers. It then scores its own result on five KPIs and tunes itself for the next run, with no human approval anywhere in the loop.

**Goals**

- A complete, demoable product that works end to end in a 2-minute demo (this is a qualifier: complete beats complex).
- Visible shortest-path logic (Dijkstra / OR-Tools on Google Maps data), as the problem setter hinted.
- A clearly agentic loop: the LLM chooses which tools to call and when.
- Uses Google services (Maps Routes API, Gemini).

**Non-goals**

- Real SMS/email delivery (mock notifications in the UI).
- Auth, multi-tenant, payments, driver mobile app.
- Real-time vehicle GPS (positions are simulated).
- More than about 20 stops or 5 vehicles.

## 3. Demo script (2 minutes)

Every feature we build must serve one of these steps. If it does not, cut it.

1. Open the app. The map shows Chennai with 10 order pins and 3 vehicles at the depot.
2. Click **Plan routes**. The agent log shows it calling the distance matrix and the optimizer. Three colored routes appear, with total distance and ETA per vehicle.
3. Click **Simulate disruption** and choose "Flooding on OMR". The affected road segment turns red on the map.
4. The agent log streams: detected disruption, identified 2 affected routes, re-optimized, new routes drawn, time saved shown.
5. Customer notification cards appear, one per affected order, each with a Gemini-written ETA message.
6. Metric cards show before vs after: total time, distance, late orders avoided.
7. (Optional) Type "Add urgent delivery to Anna Nagar by 3 PM" and watch the agent insert it into the best route.

**Feedback beat (optional, 30 seconds):** run the same disruption two more times. The agent log shows the critic scoring three candidate plans each time, the ETA error shrinks, and the KPI panel's overall score rises. No human approves anything at any point.

## 4. Architecture

The LLM only chooses which tools to call; every route number comes from the routing engine. The dashed Jev path exists only on the feature/jev branch.

&#91;embedded content: system architecture, 3 layers plus external services\]

**Pipeline for one disruption**

1. POST /api/disruptions starts an agent run.
2. (feature/jev only) Jev triages: severity, action, confidence.
3. Gemini calls apply\_disruption, then replan\_routes, then get\_affected\_orders.
4. The routing engine updates edge weights and re-solves; a route\_update event redraws the map.
5. Gemini drafts one message per affected customer in parallel; notification events appear.
6. A metrics event shows before vs after, then a done event ends the run.

**Feedback layer.** Steps 3 and 4 run inside the inner loop: the critic scores three candidate plans on the KPIs (sections 12 and 13) and only the best is applied, or the current plan is kept. After step 6 the learner compares realized and predicted outcomes and updates the policy store. No step waits for a human.

## 6. Data models and seed data

All state lives in memory, loaded from data/seed.json at startup. Use these Pydantic models in backend/app/models.py.

```python
from pydantic import BaseModel
from typing import Literal, Optional

class LatLng(BaseModel):
    lat: float
    lng: float

class Order(BaseModel):
    id: str                      # "O1"
    customer: str
    phone: str                   # mock
    address: str
    location: LatLng
    deadline_min: int            # minutes from shift start
    priority: Literal["normal", "urgent"] = "normal"
    weight_kg: float = 1.0
    status: Literal["pending", "assigned", "delivered"] = "pending"

class Vehicle(BaseModel):
    id: str                      # "V1"
    driver: str
    capacity_kg: float
    depot: LatLng
    status: Literal["active", "broken_down"] = "active"

class Route(BaseModel):
    vehicle_id: str
    stops: list[str]             # ordered order ids
    path: list[LatLng]           # decoded polyline for the map
    distance_km: float
    duration_min: float
    eta_by_order: dict[str, float]

class Disruption(BaseModel):
    id: str
    kind: Literal["flood", "traffic", "breakdown"]
    description: str
    affected_edges: list[tuple[str, str]] = []   # node id pairs, for flood/traffic
    delay_multiplier: float = 1.0                # 3.0 = three times slower
    vehicle_id: Optional[str] = None             # for breakdown

class AgentEvent(BaseModel):
    ts: float
    type: Literal["thought", "tool_call", "tool_result", "route_update", "notification", "metrics", "evaluation", "policy_update", "done"]
    payload: dict
```

## 7. Routing engine (the "shortest path" core)

Routing is deterministic code. The LLM never computes routes; it only decides which routing tool to call. Keep this layer pure and unit-tested.

**Step 1: distance matrix (matrix.py)**

- Call Google Routes API `computeRouteMatrix` once for depot plus all order locations (11 x 11 for the seed data). Use `TRAFFIC_AWARE` routing preference.
- Store a duration matrix (seconds) and a distance matrix (meters) as NumPy arrays or nested dicts.
- Cache the result to data/matrix\_cache.json keyed by a hash of the coordinates. If the API call fails or no key is set, load the cache so the demo never breaks.

**Step 2: graph and shortest path (graph.py)**

- Build a complete weighted graph in NetworkX: nodes are depot plus orders, edge weight is travel duration from the matrix.
- `shortest_path(a, b)` uses Dijkstra over this graph. Disruptions are applied by multiplying edge weights, so Dijkstra naturally routes around a flooded segment through intermediate nodes.
- Expose `shortest_path_cost(a, b)` for the VRP layer and for the UI ("direct 24 min, via Guindy 31 min").

**Step 3: multi-stop optimization (vrp.py)**

- Use OR-Tools Routing with the duration matrix: one depot, N vehicles, capacity dimension (weight\_kg), and a time dimension with per-order deadlines as soft upper bounds (late penalty) so a solution always exists.
- Urgent orders get a higher lateness penalty.
- First solution strategy `PATH_CHEAPEST_ARC`, local search metaheuristic `GUIDED_LOCAL_SEARCH`, time limit 2 seconds.
- Return a list of `Route` objects (without polylines yet).

**Step 4: polylines (matrix.py)**

- For each final route, call Routes API `computeRoutes` once per vehicle with intermediate waypoints to get the encoded polyline, then decode it into the `path` field. Cache these too.

**Re-planning rule.** When a disruption arrives, update edge weights (or mark the vehicle unavailable), keep already-delivered orders out, and re-run Step 3 for the remaining orders. Compute before vs after metrics: total duration, total distance, count of orders past deadline.

**Tests.** Cover Dijkstra on a hand-made 5-node graph, VRP returning every order exactly once, and re-planning after a vehicle breakdown reassigning its orders.

## 8. Agent design (Gemini)

The agent is a tool-calling loop: Gemini receives the situation, picks tools, sees results, and repeats until it declares the situation handled. Every step is emitted as an AgentEvent to the UI.

**LLMProvider interface (llm.py).** Wrap the model behind one interface so the Jev branch can swap or augment it without touching the loop.

```python
class LLMProvider(Protocol):
    async def decide(self, messages, tools) -> LLMStep: ...   # tool call or final text
    async def draft_message(self, order, new_eta, reason) -> str: ...
```

**Tools (tools.py).** Each tool is a plain Python function with a JSON schema passed to Gemini function calling. Tools return small JSON, never long text.

| Tool | Purpose | Calls |
| --- | --- | --- |
| get\_world\_state() | Orders, vehicles, current routes, active disruptions | state |
| plan\_routes() | Full optimization from scratch | vrp.py |
| apply\_disruption(id) | Update edge weights or vehicle status | graph.py |
| replan\_routes(reason) | Re-optimize remaining orders, return before vs after metrics | vrp.py |
| get\_shortest\_path(a, b) | Dijkstra cost and path between two nodes | graph.py |
| get\_affected\_orders() | Orders whose ETA changed by more than 5 min | state |
| notify\_customer(order\_id, message) | Mock send, emits a notification event | state |
| add\_order(...) | Insert a new order and re-plan (P2) | vrp.py |

**Feedback tools (section 13).** `evaluate_plan(plan_id)` returns the KPI grid, composite, and a verdict (apply, refine, hold). `get_policy()` returns the learned policy. No tool writes the policy: the learner updates it in plain code after each run, so the LLM cannot corrupt it.

**Loop (agent.py).**

1. Build messages: system prompt plus the trigger ("Disruption detected: flooding on OMR").
2. Call `decide()`. If it returns a tool call, run it, emit tool\_call and tool\_result events, append the result, repeat.
3. Cap at 8 iterations. On cap or error, emit an error event and fall back to the scripted pipeline: replan\_routes, then notify each affected customer.
4. When the model returns final text, emit a thought event with the summary, then a done event.

**System prompt (prompts.py).** Role: autonomous dispatch agent for a delivery fleet. Rules: never invent route data, always use tools for any number; after a disruption always call replan\_routes, then get\_affected\_orders, then notify\_customer for each; keep messages under 40 words and polite; report time saved in the final summary.

**Guardrails**

- The LLM may only act through the tools above; routing numbers always come from tool results.
- Validate tool arguments with Pydantic before executing.
- Customer messages are drafted in parallel (asyncio.gather) after the route update is already on screen.

## 12. Supply-chain metrics: 5 KPIs across 5 workflows

The supply chain cycle in this product is five workflows. Each is scored on the same five KPIs, redefined for the layer it controls, against baselines pre-computed before any run.

**Workflows:** W1 Order intake, W2 Route planning, W3 Dispatch and execution, W4 Disruption response, W5 Customer communication.

**KPIs:** K1 On-time delivery, K2 Route efficiency, K3 Cycle time, K4 Fleet utilization, K5 Resilience.

| Workflow (our layer) | K1 On-time | K2 Efficiency | K3 Cycle time | K4 Utilization | K5 Resilience |
| --- | --- | --- | --- | --- | --- |
| W1 Order intake (orders, priority) | Feasibility: % of orders whose direct depot-to-order Dijkstra time meets the deadline | Reference: MST weight over depot and orders (km), the lower bound for any plan | Mean slack: deadline minus direct travel time (min) | Demand ratio: total order kg / fleet capacity kg | Fragility: % of orders with under 15 min slack |
| W2 Route planning (matrix, Dijkstra, OR-Tools) | Planned OTD: % of orders with planned ETA at or before deadline | MST km / planned total km | Mean direct time / mean planned ETA | Mean load / capacity, blended with duration balance | Stress OTD: planned OTD with every edge x1.2 |
| W3 Dispatch and execution (simulator) | Realized OTD from the simulated day | Planned min / realized min | Mean direct time / mean realized delivery time | Vehicle busy time / shift length | 1 minus the share of planned slack consumed by delays |
| W4 Disruption response (apply\_disruption, replan\_routes) | OTD after re-plan; orders saved vs do-nothing | MST km / re-plan km on the disrupted graph | Disruption-to-new-plan latency (s), target 5 s | Duration balance after re-plan | Recovery ratio: delay recovered / delay caused |
| W5 Customer communication (notify\_customer) | Coverage: affected orders notified / affected orders | Precision: affected notified / all notified | Latency from route\_update to message (s), target 3 s | Validity: % of messages under 40 words that contain the new ETA | ETA accuracy: 1 minus mean absolute error / realized trip time |

**Scoring.** Every cell returns a raw value, a 0 to 1 score (higher is always better), its pre-computed baseline, and the delta. Formulas:

```python
# ETA[o], deadline[o] in minutes; plan_km, route_min are plan totals; n = number of orders
otd         = sum(ETA[o] <= deadline[o] for o in orders) / n
efficiency  = min(1, mst_km / plan_km)
cycle       = min(1, lower_bound_min / mean(ETA))     # lower_bound_min = mean direct depot-to-order time
balance     = 1 - (max(route_min) - min(route_min)) / max(route_min)
utilization = 0.5 * mean(load_kg / capacity_kg) + 0.5 * balance
recovery    = clamp((T_do_nothing - T_after) / (T_do_nothing - T_before), 0, 1)
latency     = min(1, target_s / actual_s)             # K3 for W4 and W5
```

Composite per workflow = weighted mean of its five scores. Overall score = mean of the five composites. Default weights live in config (metrics\_weights.json):

| Workflow | K1 | K2 | K3 | K4 | K5 |
| --- | --- | --- | --- | --- | --- |
| W1 Order intake | 0.25 | 0.10 | 0.25 | 0.20 | 0.20 |
| W2 Route planning | 0.30 | 0.30 | 0.15 | 0.15 | 0.10 |
| W3 Dispatch and execution | 0.35 | 0.15 | 0.20 | 0.15 | 0.15 |
| W4 Disruption response | 0.25 | 0.10 | 0.20 | 0.10 | 0.35 |
| W5 Customer communication | 0.30 | 0.10 | 0.20 | 0.15 | 0.25 |

**Pre-computed baselines.** Computed once, cached in data/metrics\_baseline.json (so OFFLINE\_MODE works), and recomputed only when the inputs change.

| What is pre-computed | When | Used for |
| --- | --- | --- |
| W1 order stats: MST km, direct times, slack, demand ratio | Startup, and again on add\_order | W1 KPIs and every efficiency ratio |
| Naive plan (nearest neighbor, round-robin vehicles) and its W2 KPIs | Startup | "Improvement over naive" on the KPI panel |
| Stress variant of each plan (every edge x1.2) | After each plan | W2 K5 |
| Do-nothing counterfactual: the current plan re-timed under each of the 3 disruption scenarios | Startup for the seed plan, after each plan for the live plan | W4 K1 and K5 |

**Rules**

- All KPI code is deterministic and runs in under 100 ms for 10 orders. No LLM call is involved in measuring.
- Code lives in backend/app/metrics/ (baseline.py, kpis.py, score.py). Unit-test each formula on a hand-built plan.
- W3 and W5 values are produced at run time by the simulator and the notifier; the rest come from plan data.
- GET /api/metrics returns the full 5 x 5 grid plus composites.

## 13. Feedback loop layer (closed loop, no human)

Every agent run is scored on the five KPIs by deterministic code, and that score changes how the next run plans, so the system improves itself with no human approval step anywhere.

&#91;embedded content: closed feedback loop · 6 stages, inner and outer loops\]

The inner loop is Plan and Critic (refine, at most 2 rounds). The middle loop is the whole cycle, closed by Learn. The outer loop is the optional reflection step below it.

**Why this architecture**

- The critic is code, not an LLM. Scores are repeatable, take milliseconds, and cannot be talked into approving a bad plan. The LLM proposes; it never grades itself.
- Autonomy comes from verification, not trust. When unsure, the agent builds several candidate plans and the critic picks the best. The worst case is keeping the current plan.
- Learning is bounded and reversible. Plain code updates a small policy store in capped steps and rolls back if scores fall. The LLM has no tool that writes the policy.

**Three loops**

| Loop | Runs | What it does | What it changes | Guard |
| --- | --- | --- | --- | --- |
| Inner: Plan and Critic | Every plan, about 1 to 3 s | OR-Tools solves 3 candidates (weight sets from the policy store). The critic scores each on the KPIs and picks the highest composite | The plan, before it is applied | Candidate must assign every order within capacity. If the best scores below the do-nothing baseline, refine up to 2 rounds (raise lateness penalty, re-seed); if still worse, keep the current plan |
| Middle: Measure and Learn | After every run, when the simulated day completes | Compares realized outcomes with predictions, then updates the policy store | delay\_factor per disruption kind, eta\_bias per vehicle, score\_ema per candidate | Each update capped at plus or minus 25% per run. Roll back to the previous policy version if the overall score drops two runs in a row |
| Outer: Reflection (P2) | Background, after a run | Gemini reads run summaries and proposes lessons as structured rules | The rule list in the policy store | A rule is adopted only if replaying the stored scenarios raises the composite on every one |

The inner loop scores with W2 (W4 after a disruption), because W3 and W5 only exist after execution. The middle loop scores all five workflows.

**What it learns from.** There is no real GPS, so the simulator plays the real world. It applies each scenario with a hidden true multiplier (for example flood 5.0x, plus 10% seeded noise) that differs from the agent's starting assumption (4.0x). The gap between predicted and realized ETAs is the learning signal. True values live in sim/truth.json, are never shown to the agent, and use a fixed random seed so demos repeat.

Update rule: `delay_factor[kind] = 0.5 * delay_factor[kind] + 0.5 * observed_ratio`, clamped to 25% of the previous value. Illustrative target: flood factor 4.0, then 4.5, then 4.75, and ETA error from about 20% to about 5% over three runs.

**Policy store** (data/policy.json, previous version kept in data/policy\_prev.json, written atomically)

```json
{
  "version": 3,
  "delay_factor": {"flood": 4.5, "traffic": 2.5, "breakdown": 1.0},
  "eta_bias": {"V1": 1.04, "V2": 1.00, "V3": 1.08},
  "vrp_candidates": [
    {"name": "balanced", "late_penalty": 100, "balance_weight": 0.5, "score_ema": 0.74},
    {"name": "deadline-first", "late_penalty": 400, "balance_weight": 0.1, "score_ema": 0.78},
    {"name": "compact", "late_penalty": 50, "balance_weight": 0.8, "score_ema": 0.69}
  ],
  "history": [{"run": 1, "overall": 0.71, "eta_error": 0.20}]
}
```

**Autonomy rules (replace every human approval step)**

| Situation | Automatic action |
| --- | --- |
| Best candidate scores at or above the baseline | Apply it |
| Every candidate scores below the do-nothing baseline | Keep the current plan and emit a hold event with the scores |
| A candidate leaves an order unassigned or breaks capacity | Discard that candidate |
| Jev or Gemini is unsure (top probability under 0.50) | Build all candidates and let the critic decide |
| LLM, tool, or Jev call errors or times out | Run the scripted pipeline (replan, notify) |
| Overall score drops two runs in a row | Roll back to the previous policy version |
| A reflection lesson fails replay | Discard it |

**Interfaces**

- Agent tools added: `evaluate_plan(plan_id)` returns the KPI grid, composite, and a verdict (apply, refine, hold); `get_policy()` returns the current policy. No tool writes the policy; learner.py runs after the run in plain code.
- New AgentEvent types: `evaluation` (KPIs per candidate) and `policy_update` (what changed and why).
- Endpoints: GET /api/metrics, GET /api/policy, and POST /api/reset (pass hard=true to also clear the policy; the default keeps it so learning survives between demo runs).
- Code: backend/app/feedback/ (critic.py, learner.py, policy.py).

**Demo beat (30 seconds).** Run the same disruption three times. The log shows the critic scoring three candidates each time, the ETA error falls, and the overall score rises. That is the self-improving agent moment.

## 14. Jev feature branch (feature/jev)

Build and finish the Gemini-only version on main first. Then branch to feature/jev and add Jev as a fast triage and confidence-gating layer. Gemini stays for the agent loop and customer messages. Merge only if it measurably helps and the demo still works with Jev unreachable.

**What Jev is.** A TypeSafe AI model that takes structured program state and returns typed decisions with calibrated probabilities (typically 70 to 500 ms, no free text). Docs: https://docs.typesafe.ai/ and console: https://console.typesafe.ai/. Read the docs for the exact request format and SDK before coding; do not guess the API shape.

**Jobs for Jev (only these)**

1. **Disruption triage.** Input: disruption event plus a compact world summary. Output: severity (low, medium, high), action (ignore, reroute, verify), each with a probability.
2. **Order priority scoring.** Input: an order (deadline, priority flag, customer notes). Output: urgency class with probability. Used as a penalty weight in the VRP.
3. **Order extraction (P2).** Input: messy free text. Output: structured order fields.

**Suggested triage output schema**

```json
{
  "severity": {"low": 0.05, "medium": 0.14, "high": 0.81},
  "action": {"ignore": 0.02, "reroute": 0.88, "verify": 0.10},
  "customers_likely_late": {"yes": 0.9, "no": 0.1}
}
```

**Confidence gating**

- Top action probability at or above 0.80: act automatically (run the agent loop).
- Between 0.50 and 0.80: run the agent loop and show the critic verdict next to it in the UI.
- Below 0.50: build all candidate plans and let the critic (section 13) decide; keep the current plan if none beats the baseline.
- Show the probabilities in the UI next to the agent log (a small confidence bar per decision).

**Integration points**

- Add `agent/jev_provider.py` and a `triage()` method on the provider interface; Gemini provider returns None for it.
- Feature flag `USE_JEV=true` in config. Flag off means identical behavior to main.
- In `POST /api/disruptions`, call triage first, emit a `triage` AgentEvent (add it to the event types), then continue or gate.
- Timeout of 1.5 s on Jev calls; on timeout or error, skip triage and continue with the normal agent loop, logging a warning event.
- Run Jev calls for multiple items in parallel.

**Measure it.** Log latency per Jev call and per equivalent Gemini call into a small table and show it in the UI ("triage: 0.2 s"). Test latency from the actual venue network; Jev servers are US-based, so Chennai round trip may be higher than published numbers. If the numbers are not clearly better, do not merge.
